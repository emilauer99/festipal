## Color

Hell-first (light is default per CI v1.0 §6). All values below are **role names**, never raw
hex — components resolve through `useTheme().colors` per render.

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `colors.bgApp` (Papier `#F7F5F2` light / Ink `#0C0E13` dark) | screen background — tab and both push screens |
| Secondary (30%) | `colors.surfaceCard` (`#FFFFFF` light / white 6% dark) | `ActivityCard`, `CapacityField` block, permission callouts (via `fillInfoQuiet`, see Info below), form field wrappers |
| Accent (10%) | `colors.primary` (Beere `#E8559F`) | see explicit reserved-for list below |
| Destructive | `colors.dangerText` (`#FF4D5E` dark / `#C93D4A` light-AA) | "Auflösen" action + its confirm dialog + mutation failure text |

**Accent reserved for — explicit list, nothing else:**

1. Primary CTA solid pills: "Aktivität starten" (top of tab + sectional empty-state CTA), "Los,
   posten" (create-form submit), "Beitreten" (join, when enabled) — solid `colors.primary` fill,
   `colors.textOnPrimary` text (matches `RelationAction`/`calloutPrimaryButton`/`heroCta`).
2. "Dabei" badge — on both the list card and the detail screen — `colors.fillBrandQuiet`
   background + `colors.primary` text (matches `FestivalCard`'s "Saved" badge exactly).
3. Selected state of: the single-select tag chip, the day chip, the "Standort angeheftet" chip
   once captured — `colors.fillBrandQuiet` fill + `colors.primary` border/text (mirrors
   `SegmentedControl.itemSelected`).
4. "Route öffnen" pill in the detail meeting-point block — a **secondary-accent** treatment
   (`colors.fillBrandQuiet` background, `colors.borderBrand` border, `colors.primary` text/icon)
   — deliberately NOT a second solid-primary pill on the same screen as "Beitreten"/"Verlassen".
5. `@handle` text inside every `PersonRow` (participant list) — existing, unchanged rule.
6. `AvatarTile` tint + border ring on every participant avatar — existing, unchanged rule.
7. "Einstellungen öffnen" button inside the location-permission-denied callout — matches the
   existing camera-denied callout precedent (`CameraScanPanel.tsx`'s `calloutPrimaryButton`)
   exactly; do not invent a different treatment for the second native-permission callout.

**Never accent:** tag-chip UNSELECTED state, "Gestartet" fact-chip, "Verlassen" button,
"Klonen" action, section headings, form field borders. Tag-chip color is a deliberate
deviation from the Figma-style design reference (which used an Amber-quiet fill) — this
project's token set has no quiet-Amber role, and this phase does not add one (out of the
phase's own file-touch scope). Unselected/neutral chips use `colors.fillQuiet` background +
`colors.textSecondary` text instead (same neutral-chip treatment `ListRow`'s badge and
`PersonRow`'s compact chrome already establish) — "design is direction, not wording" (house
rule, Phase 6 D-14).

**Info (non-accent semantic):** `colors.fillInfoQuiet` / `colors.borderInfo` / `colors.infoText`
— reserved for the location-permission-denied callout only, identical structure to
`CameraScanPanel`'s camera-denied callout (D-13's explicit modeling instruction).

**Destructive (danger):** `colors.dangerText` for the "Auflösen" row (icon + label, matches
`friend-detail.tsx`'s `dangerRow`/`dangerLabel` verbatim) and its native `Alert.alert`
destructive button; also every generic mutation-failure inline text in this phase
(`colors.dangerText`, `bodySm`, reused "Couldn't save — try again." pattern).

## Screens & Navigation Contract

- Both new screens are **root-level Stack siblings** of `(tabs)`, exactly like
  `cashless.tsx`/`friend-detail.tsx`/`friends-qr.tsx` — registered explicitly in
  `app/_layout.tsx`'s authenticated `Stack.Protected` block (an unregistered sibling
  dead-ends on Expo Router's Unmatched Route screen, the same failure class as the resolved
  `first-login-unmatched-route` bug).
- `apps/mobile/lib/app-chrome.ts`'s `PUSH_SCREEN_ROUTES` set and `PushScreenRoute` type gain
  two members: `'activity-create'` and `'activity-detail'`. `AppHeader`'s `pushScreenTitle`
  map gets two new **static** entries (DE/EN per the Copywriting Contract above) — the
  detail screen's title stays the fixed "Aktivität"/"Activity", not the activity's own name;
  the activity's own title renders as an in-content heading below the header (same split
  `friend-detail.tsx` uses: fixed header title, dynamic content heading).
- Both screens use `useHeaderClearance()` + `SafeAreaView edges={['bottom']}`, identical to
  `cashless.tsx`.
- **Clone is a pure UI action, no endpoint** (ADR-017): navigating `/activity-create` with a
  `cloneFromId` param, the create screen reads the source `ActivityDetail` out of the
  `activityKeys.detail(...)` React Query cache — same idiom `findCachedFriend`/
  `findCachedFestivalBySlug` already establish. If the cache entry is missing (cold process
  restart before the detail screen was ever visited), the clone param is silently ignored and
  the form opens empty — never a broken/crashing screen (same "cache miss closes gracefully"
  precedent as `friend-detail.tsx`).
- Navigation after actions (Claude's Discretion in `11-CONTEXT.md`, resolved here):
  - **Create success** → `router.replace({ pathname: '/activity-detail', params: { activityId: created.id } })` (replace, not push — back from the fresh detail screen returns to the tab, not to the empty form).
  - **Join/Leave** → no navigation; the detail screen re-renders in place once the shared mutation hook settles.
  - **Dissolve success** → `router.canGoBack() ? router.back() : router.replace to the festival's Activities tab` — same pattern `friend-detail.tsx`'s unfriend-success navigation uses, silently (no toast — matches unfriend's precedent of no confirmation toast either).
  - **Clone tap (from detail)** → `router.push` (not replace) to `/activity-create?cloneFromId=...` — back returns to the source detail screen.
- Participant list ordering: rendered in `participants` array order (`joinedAt` ascending, per
  the contract) with no extra sort — this naturally puts the creator first (they join in the
  same transaction the activity is created in, `10-CONTEXT.md` D-07) without needing a
  separate "creator" badge or a second sort key.

## Query Key & Cache Contract

```ts
// lib/activity-queries.ts — mirrors friendKeys/festivalKeys exactly
export const activityKeys = {
  all: (festivalId: string) => ['activities', festivalId] as const,
  tags: (festivalId: string) => ['activities', festivalId, 'tags'] as const,
  list: (festivalId: string) => ['activities', festivalId, 'list'] as const,
  mine: (festivalId: string) => ['activities', festivalId, 'mine'] as const,
  detail: (festivalId: string, activityId: string) =>
    ['activities', festivalId, 'detail', activityId] as const,
};
```

- `activityKeys.all(festivalId)` is the shared prefix. A single
  `queryClient.invalidateQueries({ queryKey: activityKeys.all(festivalId) })` in every
  mutation's `onSettled` (create, join, leave, dissolve) refreshes tags/list/mine/every open
  detail at once — same one-call invalidation shape `friendKeys.all` already uses.
- **"Feels immediate" contract (Success Criterion 2), reconciled with the phase's own
  online-only rule** (`REQUIREMENTS.md` Out of Scope: "activity create/join and chat send are
  online-only — no offline mutation queue"): this phase does **not** introduce a
  `setQueryData`-based optimistic cache write. It follows the existing `useFriendMutations`
  idiom exactly — `pendingTargetId`/`failedTargetId` local state disables the tapped
  control immediately (opacity `PENDING_OPACITY` pattern) while the mutation is in flight, and
  `onSettled` invalidation repaints the real numbers once the (fast, local-network) response
  lands. If the device is offline, the mutation rejects, the pending state clears, and the
  existing generic "Couldn't save — try again." inline copy applies — no queue, no silent
  retry.
- "Survives an app restart" (Success Criterion 2) means: on cold start, the persisted
  TanStack Query cache paints the last-known seat count/joined-state instantly, and the
  screen's own `useQuery` immediately issues a fresh network fetch that reconciles it — the
  same project-wide offline-first read pattern every other list in the app already follows.
  No new persistence code is needed in this phase.

## Native Capability Contract — Standort (D-13)

- **New native dependency: `expo-location`.** This is a native module addition — same class
  of change as `expo-camera` (Phase 8) and `react-native-webview` (Phase 09-06) — and MUST go
  through the manual package-legitimacy gate (publisher, repo, exact package name, dependency
  tree) **before** the install command runs, recorded as a `T-11-SC` entry in the phase's
  security register, exactly like the `T-08-SC` entries for `qrcode-generator`/`expo-camera`.
- One `Location.getCurrentPositionAsync()` call per "Standort anheften" tap — never
  `watchPositionAsync`, never a background task. This is the literal ADR-017 §2 boundary:
  the geo point is a one-off, opt-in capture for route hand-off, explicitly **not** presence
  tracking (contrast with ADR-014's ban on any "who is here" GPS signal).
- Permission flow: three sub-states, modeled 1:1 on `CameraScanPanel.tsx`'s
  `PermissionSubState` (`pending`/`granted`/`denied`) — request exactly once per mount via a
  `useRef` guard, never re-prompt on every render.
  - `pending` → the standard "Wird geladen…" text.
  - `granted` → "Standort anheften" button is live; a tap fires the one-shot position read and
    swaps the button for the removable "Standort angeheftet" chip on success.
  - `denied` → the info-toned callout (`fillInfoQuiet`/`borderInfo`/`infoText`, `r-card`
    radius) exactly matching `CameraScanPanel`'s camera-denied callout structure: icon + title
    + body + "Einstellungen öffnen" (`Linking.openSettings()`) button. **Denial is fully
    graceful — the activity is completely functional without a geo point** (free-text location
    still works, per ACT-05); nothing in the form is blocked by a denied permission.
- Requires a rationale string in `app.json`'s `expo-location` plugin config (same pattern as
  the existing `expo-camera` entry): e.g. *"quiks nutzt deinen Standort einmalig, um beim
  Erstellen einer Aktivität einen Treffpunkt zu setzen — kein Tracking."* Requires a native
  rebuild (`npx expo run:android` from `apps/mobile`, never the repo root) before device
  testing — a human checkpoint, not an autonomous executor step (same as Phase 8's camera
  rebuild).

## Route/Maps Handoff Contract (D-14, ACT-05)

- `Linking.openURL` with a platform-native URI — **no new package**, no in-app map/sheet:
  - Android: `geo:{lat},{lng}` (hands off to the device's default maps app or its own app
    chooser).
  - iOS: `https://maps.apple.com/?ll={lat},{lng}`.
- Only the activity's OWN validated `geo` object (from `activityDetailSchema.geo`, already
  `z.number().min/max`-bounded by the contract) is ever interpolated into this URI — **never**
  user-entered free text, and never a value read back out of a WebView or deep link. This is
  the phase's one security-relevant construction point (per `11-CONTEXT.md` Specific Ideas) —
  build the string from the two numeric fields only.
- Visible **only** on the detail screen's meeting-point block, and **only** when `geo` is
  non-null (D-16) — no route affordance anywhere in `ActivityCard`'s list row, no second
  entry point. When `geo` is null, the meeting-point block renders the free-text `location`
  only (or nothing, if that too is empty — never a placeholder claiming there's a location
  when there isn't).

## Auto-Title & Clone Prefill Contract

- **The server already resolves the display title** (`activitySchema.title` is always the
  final, resolved string — explicit title if set, else the localized tag title,
  `10-CONTEXT.md`). The create form only *previews* the rule client-side (D-05) — it never
  reconstructs a resolved title for display anywhere else. `canSubmitActivity(form)`
  (`lib/activity-form.ts`) is the one place the "tagId OR non-empty title" rule lives
  client-side, mirroring (never duplicating logic from) the contract's own
  `createActivityBodySchema.refine`.
- Live rule (D-05): selecting a tag makes the title field optional (its placeholder switches
  to the tag-label preview copy above) and reveals the Subtitle field; clearing the tag makes
  the title required again. Validation surfaces at submit-tap time, not on blur — inline error
  text below the title field, never a toast.
- Clone prefill (D-12/D-15): `buildClonePrefill(source: ActivityDetail)` copies
  `tag`/`title`/`subtitle`/`description`/`location`/`capacity` verbatim and **explicitly
  drops** `startTime` and `geo` — both must be re-entered. This is a deliberate, user-chosen
  deviation from the recommended default (`11-CONTEXT.md` D-15: "gegen die Empfehlung"): the
  cost (whoever clones is usually not standing at the original meeting point right now) was
  named and accepted in exchange for never surfacing a stale pin. Do not "fix" this back to
  carrying the geo point over.
- The create screen carries **no visual indication that it's in clone mode beyond the
  already-filled fields** — no banner, no "Cloned from…" copy. The prefilled state IS the
  communication (`11-CONTEXT.md` phrases it as "Zeit geleert" being sufficient signal); adding
  banner copy is out of scope for this phase.
