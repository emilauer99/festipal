für den Karten-Handoff mit seiner Spec.

Warum als eigener Plan in Welle 1: der native Rebuild ist der Langläufer dieser Phase und ein
Human-Checkpoint, kein Executor-Schritt (Windows-Session-Regel: `npx expo run:android` aus
`apps/mobile`, nie aus dem Repo-Root, Metro vorher stoppen). Wer ihn erst mit dem Create-Screen
anstößt, blockiert die Phase an ihrem spätesten Punkt. Das Paket-Legitimitäts-Gate ist zudem ein
blockierender Sicherheits-Checkpoint, der niemals automatisch durchgewunken wird — er gehört an den
Anfang.

`lib/geo-link.ts` liegt in diesem Plan, weil es die sicherheitsrelevanteste Konstruktion der ganzen
Phase ist: die einzige Stelle, an der Daten das Gerät in Richtung einer fremden App verlassen. Ihre
Härtung ist eine **Signatur**-Frage — die Funktion darf gar keinen Eingang für Freitext haben —
und keine Frage der Sorgfalt an der Aufrufstelle.

Purpose: Die native Abhängigkeit und der Grenzübertritt zur fremden Karten-App sind vor jedem
Screen entschieden und belegt.
Output: `expo-location` installiert und konfiguriert, `T-11-SC` belegt, ein nativer Build auf dem
Gerät, `buildRouteUri` samt Spec.

Screens, keine Komponenten, keine Kataloge. Er trägt keine nutzersichtbare Zeichenkette bei.

Exportiere `buildRouteUri`. Die Signatur nimmt zwei Dinge entgegen: das aus `activityGeoSchema`
abgeleitete Geo-Objekt und einen Plattform-Diskriminator. Sie nimmt **keinen** String-Parameter
entgegen — genau darin liegt die Härtung: es gibt keinen Eingang, über den der Freitext-Ort, ein
Deep-Link-Wert oder ein aus einer WebView zurückgelesener Wert je in den URI gelangen könnte
(T-11-01). Der Freitext bleibt Anzeigetext im Detail-Screen und berührt diese Funktion nie.

Rückgabe nach D-14: auf Android das `geo:`-Schema mit Breite und Länge, kommagetrennt; auf iOS die
Apple-Maps-HTTPS-URL mit dem Koordinatenpaar im `ll`-Parameter. Die Zahlen werden mit einer
locale-unabhängigen Umwandlung in den String geschrieben, damit weder ein Komma als
Dezimaltrennzeichen noch wissenschaftliche Notation entstehen kann — beides würde den URI für die
Zielanwendung unlesbar machen.

Die Spec deckt ab: beide Plattformzweige; die vier Vorzeichenkombinationen aus positiver und
negativer Breite und Länge; die vier Randwerte des Vertrags (Breite -90 und 90, Länge -180 und
180); den Nullpunkt (beide Werte 0 — der muss einen wohlgeformten URI ergeben und darf nicht als
„nicht gesetzt" durchfallen); eine Koordinate mit vielen Nachkommastellen, deren Ausgabe weder
wissenschaftliche Notation noch ein Komma als Dezimaltrennzeichen enthält. Zusätzlich ein Fall,
der die Härtung als Invariante festhält: die Ausgabe hängt ausschließlich von den beiden
Zahlenwerten und der Plattform ab — zwei Aufrufe mit denselben Koordinaten liefern denselben URI,
unabhängig davon, welcher Freitext-Ort an der Aktivität hängt.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm-Registry → `apps/mobile`-Abhängigkeitsbaum | ein neues natives Paket überschreitet sie und läuft danach mit App-Rechten |
| App → Betriebssystem-Standortdienst | eine neue OS-Berechtigung wird angefragt |
| App → fremde Karten-App | ein selbstgebauter URI verlässt die App und wird von fremdem Code interpretiert |
