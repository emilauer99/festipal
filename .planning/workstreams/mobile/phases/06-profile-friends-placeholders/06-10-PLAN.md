<objective>
Close G-06-5: opening the Profile screen crashes the app with
`TypeError: undefined cannot be used as a constructor.`

Root cause (diagnosed in `.planning/debug/profile-screen-undefined-constructor.md`, an
AND-gate of code + engine): `app/profil.tsx:199-200` is the only place in the app that
renders an ICU plural message. `@lingui/core@6.6.0` resolves any plural token by eagerly
evaluating `new Intl.PluralRules(...)`, Hermes does not implement `Intl.PluralRules`, and
the app registers no polyfill.

Fix: register `@formatjs/intl-pluralrules` at a custom Expo Router entry point, before any
route module evaluates. The `plural()` call sites are NOT touched — removing them would
mask the engine gap and forfeit the correctness 06-07 deliberately bought, and the next
plural message anywhere in the app would bring the crash straight back.

Purpose: the Profile screen is the deliverable of PROF-01 and is currently unreachable, so
the phase cannot be verified at all. Two judgment-tier UAT prohibitions (test 5 items (c)
and (d)) are also blocked behind this crash.

Output: a polyfilled Intl surface at app entry, a capability probe that makes the engine's
native support observable, and a recurrence guard that bites in the existing node-env test
runner — which is otherwise structurally blind to this whole error class.

**Task count note (4, not the usual 2-3):** two of the four tasks are zero-code gates (a
package-legitimacy checkpoint that must precede the install, and the device checkpoint that
must follow the fix). The implementation surface is two small modules plus one test file.
Splitting a strictly sequential 5-file fix across two plans would add ceremony, not safety.
</objective>

  <action>
    Wire ONE path: app process start -> polyfill installed -> Expo Router boots -> the
    existing `plural()` call sites in `app/profil.tsx` can resolve. No other layer, no
    refactor of profil.tsx.

    **Step 1 — install.** From the repo root:
    `pnpm --filter @quiks/mobile add @formatjs/intl-pluralrules@^6.3.13`
    Do NOT use `expo install` — this is a pure-JS package with no native code and no Expo
    SDK alignment, unlike 06-08's datetimepicker. Review the `pnpm-lock.yaml` diff: it must
    add `@formatjs/intl-pluralrules` and its FormatJS transitive deps and nothing else. If
    unrelated packages get relinked, stop and report rather than committing the churn.

    **Step 2 — `apps/mobile/lib/intl-capability.ts`** (new). This module must have ZERO
    imports, so that importing it first genuinely observes the engine before anything
    polyfills it. It exports one const holding `typeof Intl.PluralRules` captured at module
    evaluation time. Document in the file header WHY it is a separate module: within a
    single module every `import` is hoisted above the module body, so a capture written
    below the polyfill import would run after it and always report the polyfilled value —
    the observation would be worthless. Name the export so it reads as the NATIVE (engine)
    capability, not the current one.

    **Step 3 — `apps/mobile/lib/intl-polyfill.ts`** (new). Import order inside this file is
    load-bearing and must be preserved by anyone editing it — say so in the header:
      1. the capability probe from `./intl-capability`
      2. `@formatjs/intl-pluralrules/polyfill-force.js`
      3. `@formatjs/intl-pluralrules/locale-data/de`
      4. `@formatjs/intl-pluralrules/locale-data/en`

    Two specifier details that will look like typos to a future reader — document both
    inline so nobody "corrects" them:
      - The forced variant is deliberate. The detection variant runs its capability probe
        on every start and is documented by FormatJS as seconds-slow on Android
        (formatjs/formatjs#4463); Hermes never supports this API, so detection can only
        ever cost time and never save any.
      - The `.js` suffix on the forced-variant specifier is REQUIRED, not stylistic: the
        package's `exports` map declares the key with the extension, and this workspace
        resolves with `moduleResolution: Bundler` (packages/config/tsconfig.base.json),
        which honours `exports` strictly. The extensionless form shown in FormatJS's own
        docs does not match a key and fails to resolve. The locale-data specifiers stay
        extensionless because they match the `./locale-data/*` pattern key.

    After the imports, the module body does two things:
      - Log one startup line reporting the captured native value alongside the current
        `typeof Intl.PluralRules`. Unconditional `console.log`, matching the project's
        documented startup-info logging convention; it carries no account or user data.
        This line is the on-device evidence Task 4 collects.
      - Fail fast: if `Intl.PluralRules` is still not a function after the polyfill ran,
        throw an Error naming the missing capability and pointing at this file. A legible
        boot-time failure beats the cryptic Hermes constructor TypeError raised deep inside
        a screen render, which is what cost a whole debug session here.

    **Step 4 — `apps/mobile/index.js`** (new, 2 side-effect imports, nothing else):
    first `./lib/intl-polyfill`, then `expo-router/entry`. Expo documents this custom-entry
    pattern for exactly this purpose (router/installation, "Custom entry point to initialize
    and load side-effects") and requires `expo-router/entry` to be imported last. Keep this
    file minimal — Task 3's guard asserts its shape, and a third import here is a
    supply-chain surface (T-06-10-01).

    **Step 5 — `apps/mobile/package.json`**: set `main` to `index.js`.

    **Step 6 — cleanup**: delete the untracked `apps/mobile/profil.out.js`. It is a Babel
    transform dump left behind by the debug session that produced this plan.

    **Do NOT touch `app/profil.tsx`.** Lines 193-208 stay exactly as they are. The whole
    point of this fix is that the plural macro is correct and the engine was not.
  </action>
