## Warnings

### WR-01: Vorberechnetes Outfit-Tracking (`letterSpacing`) wird von keinem Consumer angewendet — CI §4 wird nicht gerendert

**File:** `packages/ui/src/tokens.ts:139,146,153` · Consumer: `apps/mobile/app/(auth)/welcome.tsx:78-83`, `apps/mobile/app/_layout.tsx:513-517` (SplashView), `apps/mobile/app/(auth)/email.tsx:158-162`, `apps/mobile/app/(auth)/verify.tsx:222-226`, `apps/mobile/app/(profile-setup)/complete-profile.tsx:376-379`, `apps/mobile/app/(tabs)/home.tsx:256-259,271-275`, `apps/mobile/app/(tabs)/festivals.tsx:425-429`, `apps/mobile/app/(festival)/f/[festivalSlug].tsx:266-270`, `apps/mobile/components/FestivalCard.tsx:238-242`
**Issue:** Plan 05.1-03 hat `letterSpacing` als Punkte-Werte in die `typeRoles` eingeführt (`wordmark: -2.24`, `display2: -1.76`, `title2: -0.52`), mit der Doku "precomputed from CI §4's 'Tracking −4 % bis −2 %'". Die UI-SPEC (Zeile 271) fordert die Wortmarke explizit mit "−4% tracking", und das Diskussionsprotokoll hat die Option "Voll angleichen … inkl. Outfit-Tracking" gewählt. **Kein einziger React-Native-Consumer setzt diese Werte:** Sämtliche wordmark-/display2-/title2-Styles setzen nur `fontSize`/`lineHeight`/`color` (das einzige `letterSpacing` in Screens ist das positive Micro-Eyebrow-Tracking). Konkretes Fehlerszenario: Wortmarke auf Welcome/Splash und alle Display-/Titel-Überschriften rendern mit Tracking 0 statt −4 %/−2 % — die App weicht sichtbar vom CI ab, das diese Phase verbindlich ausrollen soll, und die drei `derived`-Tokenwerte sind toter Code (nur der SVG-Glyph nutzt sein eigenes, separates `GLYPH_TEXT.letterSpacing`). Nirgendwo in den Phasen-Artefakten ist dokumentiert, dass das RN-Anwenden bewusst vertagt wurde (anders als der explizit geparkte otpDigit/countdown-Weight-Gap).
**Fix:** Tracking in den betroffenen Styles aus dem Token beziehen, z. B. in `welcome.tsx`/`_layout.tsx`:
```ts
wordmark: {
  fontSize: typeRoles.wordmark.size,
  lineHeight: typeRoles.wordmark.size * typeRoles.wordmark.lineHeight,
  letterSpacing: typeRoles.wordmark.letterSpacing,
  color: colors.textPrimary,
},
```
(analog `display2`/`title2`-Consumer). Falls das Anwenden bewusst auf eine Folgephase verschoben ist (Layout-Shift auf allen Screens), das als KNOWN FOLLOW-UP im Token-Docstring dokumentieren — sonst behauptet der Docstring einen gerenderten CI-Wert, den es nicht gibt.

### WR-02: CLAUDE.md behauptet weiterhin "Light mode is not wired up in code today" — von genau dieser Phase widerlegt

**File:** `CLAUDE.md:23-25`
**Issue:** Der Brand-Abschnitt wurde in dieser Phase aktualisiert (ADR-024 "has LANDED"), aber der Satz "Light mode is not wired up in code today (`lightColors` exported from `packages/ui/src/tokens.ts` but unused in `apps/mobile`) — that is follow-up phase work." blieb stehen. Er ist seit Plan 05.1-04 falsch: `apps/mobile/lib/theme.ts` konsumiert `lightColors`, hell-first macht Light sogar zum Default. Konkretes Fehlerszenario: CLAUDE.md ist in diesem Repo bindende Arbeitsanweisung für zukünftige Agent-Sessions — eine spätere Änderung könnte auf Basis dieser Zeile Light-Mode-Testing überspringen oder Light-Mode-Wiring "nachimplementieren".
**Fix:** Zeilen 23-25 ersetzen durch z. B.: "Hell-first (light-first): Papier `#F7F5F2` is the default surface; `apps/mobile/lib/theme.ts` resolves the device scheme (only exact `'dark'` yields the night-shift set, everything else resolves to `lightColors`)."

### WR-03: `trustedOrigins` führt `exp://` + `exp://**` bedingungslos — auch in Produktion, entgegen der eigenen Allowlist-Hygiene-Begründung

**File:** `apps/api/src/auth/auth.instance.ts:34-35`
**Issue:** Vorbestehend (nicht in dieser Phase eingeführt), aber die Phase hat genau diesen Block editiert und in den neuen Kommentarzeilen 30-32 das Prinzip formuliert: "a transitional both-schemes state would be a permanently widened origin allowlist (T-05.1-02)". Dasselbe Prinzip wird zwei Zeilen tiefer verletzt: `'exp://'` und der Wildcard `'exp://**'` sind laut Kommentar "dev-only, never used in prod builds", stehen aber ohne jedes Env-Gate dauerhaft in der Allowlist — auch im Railway-Production-Deployment. Konkretes Fehlerszenario: Jeder Client, der einen `expo-origin: exp://<beliebig>`-Header setzen kann (der `expo()`-Plugin übersetzt ihn in `origin`), passiert den CSRF-/Origin-Check der Produktions-API. Das praktische Risiko ist begrenzt (Browser können den Header cross-origin nicht setzen), aber die Allowlist ist messbar weiter als nötig und widerspricht dem dokumentierten Threat-Model-Anspruch.
**Fix:** Die beiden Dev-Einträge env-gaten:
```ts
trustedOrigins: [
  'quiks://',
  ...(env.NODE_ENV !== 'production' ? ['exp://', 'exp://**'] : []),
],
```
(`NODE_ENV` ggf. im Zod-Env-Schema `apps/api/src/config/env.ts` ergänzen.)

### IN-03: `micro`-Rolle wird inkonsistent mit/ohne Caps gerendert

**File:** `apps/mobile/components/FestivalCard.tsx:262-265` (badgeText), `274-282` (saveButtonText), `apps/mobile/components/FloatingNav.tsx:233-235` (label), `apps/mobile/components/ComingSoonTile.tsx:78-81` (badgeText) vs. `apps/mobile/app/(tabs)/home.tsx:243-249` (eyebrow), `apps/mobile/app/(profile-setup)/complete-profile.tsx:439-445` (requiredBadge)
**Issue:** `packages/ui/src/tokens.ts:169` definiert die Micro-Rolle als CI "10,5 **caps**" und delegiert das All-Caps-Rendering explizit an den Consumer (`textTransform`). Zwei Consumer setzen `textTransform: 'uppercase'` (+ positives Tracking), vier weitere (Saved/Save-Badges, Tab-Labels, Soon-Badge) nicht — dieselbe Rolle rendert also mal caps, mal mixed case. Möglicherweise designgewollt (Tab-Labels in Caps wären ungewöhnlich), dann trägt aber die Rollen-Doku die falsche Verallgemeinerung.
**Fix:** Entweder die vier Nicht-Caps-Stellen auf `textTransform: 'uppercase'` ziehen oder den Token-Kommentar präzisieren, welche Micro-Verwendungen caps sind (Eyebrow/Required-Badge) und welche nicht.
