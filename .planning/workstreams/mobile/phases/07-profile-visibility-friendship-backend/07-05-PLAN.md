**(a) Zod-Walker.** Eine lokale Hilfsfunktion, die aus einem beliebigen Zod-Schema rekursiv alle
Objekt-Schlüsselnamen sammelt. Sie behandelt ZodObject (über `.shape`), ZodArray (Elementtyp unter
`._def.type`), ZodNullable und ZodOptional (innerer Typ unter `._def.innerType`) und ZodUnion
(Varianten unter `._def.options`); alles Übrige liefert eine leere Menge. Rekursionsschutz über ein
`Set` besuchter Schemaobjekte, damit ein selbstbezüglicher Vertrag den Test nicht aufhängt.

**(b) Contract-Walk über ALLE Routen.** Über `Object.entries(contract)` iterieren und für jede Route
die Schlüsselmenge jeder Antwort einsammeln. Zwei Zusicherungen:
- Der Schlüsselname des Geburtsdatums darf nur in den Antworten von `getMe` und `completeProfile`
  vorkommen. Für jede andere Route ist er abwesend.
- Der Schlüsselname `email` darf nur in der Antwort von `getMe` vorkommen.
Wichtig für die Absicht: der Test iteriert **nicht** über eine Liste von Fremd-Routen, sondern über
*alle* Routen mit einer Ausnahmeliste. Nur so wird er rot, wenn eine künftige Phase eine **neue**
Route einführt, die eines der beiden Felder nach draussen trägt — eine Positivliste würde eine neue
Route stillschweigend ignorieren.

**(c) Feldmenge der Fremd-View festnageln.** `Object.keys(visitorProfileForeignSchema.shape)`
sortiert vergleichen mit der erwarteten Sechserliste (`accountId`, `avatar`, `displayName`,
`gender`, `pronoun`, `username`). Dieser Test ist der Grund, warum eine später hinzugefügte
Profilspalte nicht unbemerkt öffentlich wird: sie taucht in der Fremd-View nur auf, wenn jemand sie
explizit pickt, und dann bricht dieser Vergleich.

**(d) Alle vier Fremd-Pfade tragen dieselbe Projektion.** Für `lookupVisitor`, `searchVisitors`,
`listFriends` und `listFriendRequests` das eingebettete `profile`-Objektschema aus der jeweiligen
200-Antwort herausziehen (die Verschachtelungsorte stehen im `<interfaces>`-Block oben) und
`Object.keys(...)` sortiert auf **Gleichheit** mit der Sechserliste prüfen — nicht auf Teilmenge.
Gleichheit ist die stärkere und hier richtige Zusicherung: eine Teilmengenprüfung würde einen Pfad
durchlassen, der ein Feld weniger liefert, und damit die Behauptung „dieselbe Projektion"
verwässern.

**(e) Endpunkt-Inventar gegen einen 1:1-Nachrichtenpfad (ADR-020).** Über alle Routen die
`path`-Werte einsammeln und zusichern, dass keiner davon einen Direktnachrichten-Pfad beschreibt —
geprüft gegen eine Liste verbotener Pfadsegmente, die den Direktnachrichten-Wortschatz abdeckt.
ADR-020 schliesst 1:1-Nachrichten dauerhaft aus; eine Freundschaft impliziert keinen Kanal. Derselbe
Test ist die Grundlage für Erfolgskriterium 1 von Phase 12, das eine Endpunkt-Inventar-Zusicherung
ausdrücklich statt einer Sichtprüfung fordert — hier entsteht sie zum ersten Mal.

**(f) Quellcode-Singularität.** Alle `.ts`-Dateien unter `apps/api/src/friendship/` einlesen und
zusichern:
- `export const foreignProfileColumns` kommt über das gesamte Verzeichnis genau einmal vor.

- In `friendship.service.ts` ist die Zahl der Vorkommen von `from(visitorProfile)` gleich der Zahl
  der Vorkommen von `foreignProfileColumns` — jeder Select über die Profiltabelle benutzt die eine
  Select-Map, keiner formuliert eine eigene Spaltenliste.
- Keine Datei unter `apps/api/src/friendship/` referenziert die Geburtsdatumsspalte der

   Abwesenheitszusicherungen (im Body von visitor1 gegen visitor2s Werte).
5. **Freundesliste (Pfad 4):** visitor2 nimmt über
   `POST /api/v1/me/friend-requests/{accountIdVon1}/accept` an -> 200. Dann `GET /api/v1/me/friends`
   als visitor1 -> genau ein Eintrag mit visitor2, und dieselben drei Abwesenheitszusicherungen auf
   dem serialisierten Body.
6. **Owner-Gegenprobe:** `GET /api/v1/me` als visitor2 liefert das eigene Geburtsdatum — der
   Schlüssel ist vorhanden und der Wert stimmt mit der Fixture-Konstante überein. Das trennt
   „Split funktioniert" von „Feld wurde überall entfernt".
7. **Festival-Unabhängigkeit, Teil 1 (Erfolgskriterium 3):** Die Freundschaft besteht, obwohl
   visitor2 überhaupt kein Festival gespeichert hat — `GET /api/v1/me/friends` als visitor2 liefert
   visitor1. Eine Freundschaft braucht also keinen gemeinsamen Festivalkontext.
8. **Festival-Unabhängigkeit, Teil 2:** visitor1 speichert zusätzlich Festival B; danach ist
   `GET /api/v1/me/friends` als visitor1 byte-identisch zum Ergebnis vor dem Speichern (Vergleich
   der serialisierten Bodies). Der Satz gespeicherter Festivals hat keinen Einfluss auf die
   Freundesliste.
9. **Schema-Nachweis (SEC-02-Erfüllung für diese Phase):** Eine `information_schema.columns`-Abfrage
   über die lebende DB liefert für `friendship` und `friend_request` keine Spalte, deren Name auf
   Festival verweist. Ausserdem: die Spaltenliste beider Tabellen entspricht genau der erwarteten
   Menge, damit eine später stillschweigend hinzugefügte Spalte auffällt.
10. **Kein Zugriff ohne Session:** Jeder der vier Fremd-Endpunkte ohne Cookie -> 401. Isolation ist
    in diesem Projekt Daten-Scoping und kein Zugriffsgate (ADR-014), aber der globale AuthGuard ist
    die Vorbedingung, unter der das Scoping überhaupt greift.
