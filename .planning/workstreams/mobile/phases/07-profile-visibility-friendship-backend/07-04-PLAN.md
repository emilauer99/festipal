**(a) Contract-Formen** in `packages/contracts/src/schemas.ts`, alle mit dem eingebetteten
`profile`-Feld, damit die vier D-04-Pfade dieselbe äussere Form haben und Plan 07-05 den Contract
maschinell ablaufen kann:
- `friendSchema = z.object({ profile: visitorProfileForeignSchema, friendsSince: z.string() })`
  plus `export type Friend`.
- `friendRequestItemSchema = z.object({ profile: visitorProfileForeignSchema, requestedAt: z.string() })`.
- `friendRequestListsSchema = z.object({ incoming: z.array(friendRequestItemSchema), outgoing: z.array(friendRequestItemSchema) })`.
Kein Element trägt eine `relation` — in der Freundesliste ist sie konstant `friends`, in den
Anfragelisten steckt die Richtung schon in der Listenzugehörigkeit. Redundanz hier wäre eine
zweite Quelle für denselben Fakt.

**(b) Router-Einträge** in `packages/contracts/src/router.ts`:
- `listFriends`: `GET /me/friends`, `responses: { 200: z.array(friendSchema) }`
- `listFriendRequests`: `GET /me/friend-requests`, `responses: { 200: friendRequestListsSchema }` —
  ein kombinierter Endpunkt für beide Richtungen, weil Phase 8 sie immer gemeinsam anzeigt und ein
  zweiter Roundtrip nur Latenz kostet.
- `unfriend`: `DELETE /me/friends/:accountId`, `pathParams: z.object({ accountId: z.string() })`,
  `responses: { 200: mutationResultSchema }`
Die Pfade `/me/friend-requests` (GET, hier) und `/me/friend-requests` (POST, aus 07-03) sind
verschiedene Methoden auf derselben Ressource und damit eigenständige Route-Keys.

**(c) `pickForeignProfile` in `apps/api/src/friendship/visitor-projection.ts`.** Ergänze eine
exportierte Funktion, die ein Ergebniszeilenobjekt in das `profile`-Objekt der Fremd-View überführt.
Sie ist ab jetzt die **einzige** Stelle, an der Fremd-Profilfelder namentlich zu einem
Antwortobjekt zusammengesetzt werden — jeder Listenpfad ruft sie auf, statt die Feldnamen erneut
aufzuzählen. Zusammen mit `foreignProfileColumns` (die einzige Select-Map) ist damit sowohl das
Lesen als auch das Formen der Fremd-View an genau einem Ort.

**(d) `listFriends(callerId: string): Promise<Friend[]>`** in `friendship.service.ts`.
Ein Join von `friendship` auf `visitorProfile`, dessen Bedingung den Aufrufer in genau einer der
beiden Paarspalten sucht und die jeweils andere als Gegenüber auflöst:
`or(and(eq(friendship.lowerId, callerId), eq(visitorProfile.accountId, friendship.higherId)), and(eq(friendship.higherId, callerId), eq(visitorProfile.accountId, friendship.lowerId)))`.
Diese Bedingung filtert und wählt in einem — genau deshalb braucht die eine Zeile pro Freundschaft
keine Spiegelzeile. Selektiert wird `foreignProfileColumns` plus `friendship.createdAt`, sortiert
nach `asc(visitorProfile.username)`. Das Ergebnis wird über `pickForeignProfile` und `toIsoString`
zu `{ profile, friendsSince }`.
Falls Drizzle in dieser Version eine verschachtelte Select-Map (`{ profile: foreignProfileColumns, … }`)
nicht akzeptiert, `foreignProfileColumns` flach selektieren und das `profile`-Objekt ausschliesslich
über `pickForeignProfile` bilden — unter keinen Umständen die Feldnamen am Aufrufort erneut
auflisten.

**(e) `listRequests(callerId: string)`** -> `{ incoming: FriendRequestItem[]; outgoing: FriendRequestItem[] }`.
Dieselbe Join-Form über `friendRequest`, zusätzlich `friendRequest.requesterId` und
`friendRequest.createdAt` selektiert, sortiert nach `asc(visitorProfile.username)`. Partitionierung
in JavaScript: ist `requesterId` gleich `callerId`, gehört die Zeile nach `outgoing`, sonst nach
`incoming`. Es gibt kein Statusfeld, das hier zu prüfen wäre — die Richtung folgt allein aus
`requesterId` (D-12). Beide Listen sind immer Arrays, auch leer.

**(f) `unfriend(callerId: string, targetAccountId: string): Promise<{ status: 'removed' }>`.**
Paar über `canonicalPair` bilden, aus `friendship` löschen. Immer `'removed'`, auch wenn nichts
gelöscht wurde — idempotent und ohne Auskunft darüber, ob eine Freundschaft bestand. Da es nur eine
Zeile pro Paar gibt, ist ein einzelnes Delete für beide Seiten wirksam; es gibt keine zweite Zeile,
die vergessen werden könnte.

**(g) Controller.** Drei weitere `@TsRestHandler`-Methoden in `friendship.controller.ts`, jede mit
`@Session() session: UserSession` und `session.user.id` als einzige Quelle des Aufrufers. Keine der
drei nimmt einen Aufrufer-Parameter entgegen; bei `unfriend` ist der `:accountId` im Pfad
ausschliesslich das Gegenüber.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → API (`/me/friends`, `/me/friend-requests`, `DELETE /me/friends/:accountId`) | Ein authentifizierter Besucher liest seine eigene Beziehungsmenge und löscht eine Beziehung |
| Session → Service | Die Listenscopes sind session-abgeleitet; ein Client darf die Liste eines anderen nicht erhalten |
| Service → Postgres | Eine Zeile pro Freundschaft, aus zwei Perspektiven aufgelöst |
