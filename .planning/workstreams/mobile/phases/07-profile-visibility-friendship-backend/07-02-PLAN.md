**(a) Contract.** In `packages/contracts/src/schemas.ts`:
`visitorSearchQuerySchema = z.object({ q: z.string() })`. In `packages/contracts/src/router.ts` der
neue Eintrag `searchVisitors`: `method: 'GET'`, `path: '/visitors'`,
`query: visitorSearchQuerySchema`, `responses: { 200: z.array(visitorSummarySchema) }`. Kein
404-Fall — eine Suche ohne Treffer ist eine leere Liste, kein Fehler. Der Pfad `/visitors` steht
neben dem in 07-01 angelegten `/visitors/:username`; beide sind eigenständige Route-Keys und
kollidieren nicht.

**(b) Batchfähige Relationsauflösung.** Baue in `friendship.service.ts` die Auflösung so um, dass
es genau **eine** Implementierung gibt:
`resolveRelations(callerId: string, targetAccountIds: string[]): Promise<Map<string, Relation>>`.
Sie setzt für `callerId` selbst `'self'`, führt dann **genau zwei** Abfragen aus:
- gegen `friendship` mit
  `or(and(eq(friendship.lowerId, callerId), inArray(friendship.higherId, ids)), and(eq(friendship.higherId, callerId), inArray(friendship.lowerId, ids)))`
  — jede Trefferzeile setzt den jeweils anderen Teilnehmer auf `'friends'`.
- gegen `friendRequest` mit derselben Bedingungsform, zusätzlich `requesterId` selektiert — ist
  `requesterId` gleich `callerId`, wird `'requestOutgoing'` gesetzt, sonst `'requestIncoming'`.
Alles Übrige bleibt `'none'`. Ein leeres `ids`-Array darf keine Abfrage auslösen.
Das bestehende `resolveRelation` (Einzahl) aus 07-01 wird zu einem dünnen Delegator auf
`resolveRelations` — es darf danach keine zweite Stelle mehr geben, die Freundschafts- oder
Anfragezeilen zu einem Beziehungsstatus interpretiert.

**(c) `searchByUsername(callerId: string, q: string): Promise<VisitorSummary[]>`.**
1. `const term = q.trim()`. Ist `term.length < 2`, sofort `[]` zurückgeben — **ohne** Datenbankzugriff
   (D-08). Die Untergrenze ist eine Service-Invariante, keine Client-Konvention.
2. LIKE-Muster bauen und dabei die Musterzeichen entschärfen: Backslash, Prozentzeichen und
   Unterstrich im Suchbegriff werden mit einem Backslash maskiert, danach wird das
   Prozentzeichen als Präfix-Platzhalter angehängt. Der Unterstrich ist im erlaubten
   Username-Charset (`[a-z0-9_.]`) enthalten und gleichzeitig ein LIKE-Einzelzeichen-Platzhalter —
   ohne Maskierung würde eine Suche nach `max_muster` auch `maxXmuster` treffen. Die
   Vergleichsbedingung lautet damit
   `sql\`lower(${visitorProfile.username}) like ${pattern} escape '\\\\'\`` mit dem in JavaScript
   berechneten, kleingeschriebenen `pattern`. Nie per String-Konkatenation ins SQL schreiben —
   Drizzles `sql`-Template parametrisiert den Wert.
3. `.select(foreignProfileColumns).from(visitorProfile)` mit dieser Bedingung,
   `.orderBy(asc(visitorProfile.username))` und `.limit(20)` (D-08: stabile Ordnung, kein
   Relevanz-Ranking, harter Deckel). `displayName` wird **nicht** durchsucht (D-09) — er taucht
   nirgends in der `where`-Bedingung auf.
4. Die accountIds der Treffer einmal durch `resolveRelations` schicken und je Treffer
   `{ profile, relation }` bauen.

**Bekannte Eigenschaft, bewusst nicht behoben:** Ein B-Tree-Index unter der Default-Collation
unterstützt `LIKE 'präfix%'` nur mit `text_pattern_ops`; der vorhandene Functional Index
`visitor_profile_username_lower_unq` hat das nicht, Postgres fällt für die Suche also auf einen
Seq-Scan zurück. D-06 legt ausdrücklich fest, dass kein neues Index-Design entsteht (insbesondere
kein `pg_trgm`), und bei den Datenmengen von v1.1 ist der Unterschied bedeutungslos. Als bekannte
Eigenschaft im Doc-Kommentar der Methode festhalten, nicht beheben.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → API (`GET /visitors?q=`) | Frei wählbarer Suchstring eines authentifizierten, beliebigen Besuchers |
