**Migration erzeugen.** `pnpm --filter @quiks/db db:generate --custom --name=activity_capacity_guard`
legt eine leere `0010_*.sql` samt Journal-Eintrag an, ohne den Schema-Snapshot zu verändern — genau
der von Drizzle vorgesehene Weg für DDL, die der Differ nicht kennt (Trigger). Erzeuge sie **nicht**
von Hand, sonst driften Snapshot und Journal.

**Inhalt.** Schreibe in die generierte Datei zuerst die Funktion, dann — getrennt durch genau einen
`--> statement-breakpoint`-Marker — den Trigger. **Setze keinen Breakpoint-Marker innerhalb des
`$$ ... $$`-Funktionsrumpfs**: der Migrator zerlegt die Datei an diesen Markern, und ein Marker im
Rumpf zerschneidet die Funktion.

Die Funktion `activity_capacity_guard()` (`RETURNS trigger`, `LANGUAGE plpgsql`) tut in dieser
Reihenfolge:

1. `SELECT a.capacity INTO cap FROM activity a WHERE a.id = NEW.activity_id FOR UPDATE;`
   — **`FOR UPDATE` ist der tragende Teil.** Die Sperre liegt auf der *Elternzeile*, nicht auf einem
   Zählergebnis: ein zweiter Beitritt blockiert hier, bis der erste committet hat, und zählt danach
   den bereits geschriebenen Platz mit. Ohne die Sperre lesen beide Transaktionen unter READ
   COMMITTED denselben Zählerstand und beide kommen durch.
2. `IF NOT FOUND THEN RETURN NEW; END IF;` — kein Aktivitätstreffer; der Fremdschlüssel weist die
   Zeile ohnehin ab, der Trigger maßt sich diese Entscheidung nicht an.
3. `IF EXISTS (SELECT 1 FROM activity_participant p WHERE p.activity_id = NEW.activity_id AND p.visitor_id = NEW.visitor_id) THEN RETURN NEW; END IF;`
   — **notwendig, nicht kosmetisch.** `BEFORE INSERT`-Trigger feuern in Postgres *vor* der
   Konfliktauflösung von `ON CONFLICT DO NOTHING`. Ohne diesen Zweig würde ein bereits beigetretener
   Besucher, der denselben Beitritt wiederholt, an einer vollen Aktivität mit „voll" abgewiesen,
   obwohl er längst drin ist — die Idempotenz des Beitretens würde von der Kapazitätsprüfung
   gefressen.
4. `IF cap IS NULL THEN RETURN NEW; END IF;` — D-08: keine Kapazität heißt unbegrenzt.
5. `SELECT count(*) INTO taken FROM activity_participant p WHERE p.activity_id = NEW.activity_id;`
   Der Zähler schließt den Creator ein — D-07: `capacity` ist die Gesamtplatzzahl inklusive Creator.
6. `IF taken >= cap THEN RAISE EXCEPTION ... USING ERRCODE = 'check_violation', CONSTRAINT = 'activity_capacity_full_chk'; END IF;`
   — `ERRCODE = 'check_violation'` ergibt SQLSTATE 23514, und die `CONSTRAINT`-Option füllt das
   `constraint_name`-Feld des Fehlerreports. Genau dieses Feld liest der Service in Task 2, wie
   `friendship.service.ts` seine beiden 23505 auseinanderhält. Der Name ist bewusst nicht
   `activity_capacity_positive_chk` — die beiden Kapazitätsfehler müssen unterscheidbar bleiben.
7. `RETURN NEW;`

Der Trigger: `CREATE TRIGGER activity_participant_capacity_trg BEFORE INSERT ON activity_participant
FOR EACH ROW EXECUTE FUNCTION activity_capacity_guard();`

**[BLOCKING] Anwenden.** `pnpm --filter @quiks/db db:migrate`. Ohne diesen Schritt ist jeder
folgende Kapazitätstest falsch-grün, weil Build und Typecheck den Trigger nicht kennen.

**Contract.** In `packages/contracts/src/schemas.ts`:
`activityJoinResultSchema = z.object({ result: z.literal('joined') })` mit Typ `ActivityJoinResult`.
Für Leave und Delete wird das bestehende `mutationResultSchema` (`{ result: 'removed' }`)
wiederverwendet — kein zweites Schema für dieselbe Aussage.

In `packages/contracts/src/router.ts` drei Routen, alle mit
`pathParams: z.object({ festivalId: z.string().uuid(), activityId: z.string().uuid() })`:

- `joinActivity` — `POST /festivals/:festivalId/activities/:activityId/join`, `body: z.object({})`,
  `responses: { 200: activityJoinResultSchema, 404: errorSchema, 409: errorSchema }`.
  Summary hält fest: idempotent (zweimal beitreten ist derselbe Zustand), 409 für voll, für
  bereits gestartet und für einen Aufrufer ohne abgeschlossenes Profil, 404 für eine in diesem
  Festival unbekannte Aktivität.
- `leaveActivity` — `POST /festivals/:festivalId/activities/:activityId/leave`, `body: z.object({})`,
  `responses: { 200: mutationResultSchema, 409: errorSchema }`.
  **Kein 404-Zweig**: Verlassen ist evidenzfrei wie `decline`/`withdraw`/`unfriend` — dieselbe
  200-Antwort, ob eine Teilnahme bestand oder nicht, und auch für eine Aktivität, die es in diesem
  Festival nicht gibt. Der einzige andere Ausgang ist 409 für den Creator (D-09).
- `deleteActivity` — `DELETE /festivals/:festivalId/activities/:activityId`,
  `responses: { 200: mutationResultSchema, 404: errorSchema, 409: errorSchema }`.
  Hier ist die Antwort **bewusst nicht** evidenzfrei, und der Kommentar sagt warum: „Auflösen" ist
  eine sichtbare Zustandsänderung, die der Client rendert. Ein nicht-Creator, der eine 200 bekäme,
  würde die Karte aus seiner Liste entfernen, obwohl die Aktivität weiterläuft. Die Existenz einer
  Aktivität ist innerhalb ihres Festivals ohnehin öffentlich (Discovery), es gibt hier also kein
  Geheimnis zu schützen: 404 für unbekannt, 409 für „nicht dein", 200 für erledigt.

**Service.** In `apps/api/src/activity/activity.service.ts` drei Methoden mit diskriminierten
Ergebnissen (nie geworfene Exceptions für erwartete Konflikte):

- `join(visitorId, festivalId, activityId)`:
  `{ status: 'joined' } | { status: 'not-found' } | { status: 'full' } | { status: 'started' } | { status: 'profile-required' }`.
  Aktivität über `and(eq(activity.id, activityId), eq(activity.festivalId, festivalId))` laden —
  **beide** Bedingungen im WHERE, sonst kann eine Aktivität aus einem fremden Festival über einen
  geratenen Pfad beigetreten werden. Nicht gefunden → `not-found`. `startTime <= now()` →
  `started` (D-10: Beitreten schließt mit dem Start; der Vergleich läuft serverseitig gegen die
  DB-Zeit, nicht gegen eine Client-Angabe). Danach
  `insert(activityParticipant).values({ activityId, festivalId, visitorId }).onConflictDoNothing()`
  in einem `try`. Im `catch` über `postgresErrorOf`: `23514` mit
  `constraint_name === 'activity_capacity_full_chk'` → `full`; `23503` → `profile-required`;
  alles andere weiterwerfen. Erfolg → `joined` — auch dann, wenn `onConflictDoNothing` nichts
  geschrieben hat, weil die Teilnahme schon bestand.
- `leave(visitorId, festivalId, activityId)`:
  `{ status: 'removed' } | { status: 'creator' }`.
  Aktivität laden (beide Scope-Bedingungen). Nicht gefunden → `removed` (evidenzfrei).
  `activity.creatorId === visitorId` → `creator`; die Teilnehmerzeile bleibt unangetastet, es gibt
  keinen versteckten Nebeneffekt (D-09). Sonst DELETE auf `activity_participant` über den
  vollständigen Primärschlüssel → `removed`, unabhängig von der getroffenen Zeilenzahl.
- `remove(callerId, festivalId, activityId)` (das „Auflösen"):
  `{ status: 'removed' } | { status: 'not-found' } | { status: 'not-creator' }`.
  Aktivität laden (beide Scope-Bedingungen). Nicht gefunden → `not-found`.
  `creatorId !== callerId` → `not-creator`. Sonst `delete(activity)` über id + festivalId; die
  Teilnehmerzeilen verschwinden über die `onDelete: 'cascade'` des zusammengesetzten
  Fremdschlüssels aus 10-02 — dieselbe Kaskade, an die Phase 12 die Chat-Historie hängt.

**Controller.** Drei Handler nach der bestehenden Form, jeder mit `@Session() session: UserSession`.
`visitorId`/`callerId` immer `session.user.id`; `festivalId` und `activityId` immer aus `params`.
Mapping: `not-found` → 404; `full`/`started`/`profile-required`/`creator`/`not-creator` → 409 mit je
eigener, sprechender Meldung; sonst 200.
