# Phase 8 — UI Design Contract

> Visual and interaction contract for the real Friends screen (search/handle add, QR add, requests
> both directions, crew list, friend detail + unfriend) plus the new QR screen and the camera
> permission surfaces. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **North-star source:** `docs/concept/designs/quiks-v2/quiks-screens.template.html` — `03 Friends`
> (L1435–1491). `08-CONTEXT.md` (D-01…D-16) is authoritative for scope and is user-locked; this
> document transcribes it into pixel/token/copy contracts and resolves every "Claude's Discretion"
> item the context left open for this agent. Where a design element is explicitly REMOVED by a
> decision (Chats block D-05, "Vielleicht kennst du" D-06, the `presence` dot D-11), it is not
> reproduced anywhere below — that is deliberate, not an omission.
>
> This is not greenfield. Phase 6 already built `FriendsScreen` as an honest placeholder; this
> phase makes four of its six blocks real and deletes two. Every value below is either an EXISTING
> token/component from `packages/ui/src/tokens.ts` / `apps/mobile/components/`, or is explicitly
> flagged **NEW** with its derivation shown. Do not invent parallel values.

## Spacing & Layout Scale

The project's real ported CI ramp (`spacingScale`/`layout`/`radiiScale` in `packages/ui/src/tokens.ts`) — **unchanged this phase**, same precedent as every prior phase. Do not round toward a generic 4/8/16/24/32/48/64 scale; this is the binding brand ramp.

| Token | Value | Usage this phase |
|-------|-------|-------------------|
| `spacingScale['sp-2']` | 4px | icon↔label gaps inside pill buttons |
| `spacingScale['sp-4']` | 8px | row internal gaps (avatar↔text, text↔action) |
| `spacingScale['sp-5']` | 12px | list row gaps (search hits, requests, crew) — the design's literal `10px` rounds to this token, same tolerance Phase 6 already applied to its own 10px list gaps |
| `spacingScale['sp-6']` | 16px | card/row padding (`PersonRow`, quiks-code card, confirmation card, denied-permission callout) |
| `spacingScale['sp-8']` | 24px | pill-button horizontal padding; QR screen top-level gaps |

| `layout.sectionGap` | 28px | gap between Friends' top-level blocks (search · code card · requests · crew) |
| `layout.hitMin` | 44px | minimum tap target — every row action, every plain-text action link, the SegmentedControl on the QR screen. Applies even where the design's own pixel hint (`36px`) is smaller — same override the existing `retryButton`/`qrButton` styles already apply |

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `colors.bgApp` (Papier `#F7F5F2` light / Ink `#0C0E13` dark) | Screen background — Friends, QR screen |
| Secondary (30%) | `colors.surfaceCard` (`#FFFFFF` light / 6% white dark) | `PersonRow`, quiks-code card, confirmation card, QR mark's outer screen background |
| Accent (10%) | `colors.primary` (Beere `#E8559F`, mode-invariant) + `colors.gradientSunset` (mode-invariant, one surface only) | see reserved-for list below |
| Info (new use this phase) | `colors.fillInfoQuiet` / `colors.borderInfo` / `colors.infoText` (all **existing since Phase 6**, no new token) | Camera-permission-denied callout — informational, not an error the visitor caused |
| Destructive | `colors.dangerText` (text/icon only — never the bare `colors.danger` fill as text) | "Freundschaft beenden" row label + icon inside the friend detail card; "not a quiks code" / lookup-failed error text |

**Accent reserved for** (explicit — never "all interactive elements"):

1. `FloatingNav` active tab pill background (`fillBrandQuiet`) + active icon/label (`primary`) — unchanged from Phase 5.1/6.
2. `AvatarTile` border + initials text (`primary`) — unchanged, now also used at the new small (40px) row size (§ Avatar Size Contract) and the existing 88px size in the friend detail card.
3. `@username` text in every `PersonRow` and in the friend detail card — **new usage this phase**, but the same "brand text" precedent Phase 6 already established for the quiks-code handle (`colors.primary` on a mono/body run). Applies uniformly to search hits, request rows and crew rows — one rule, no per-list exception.
4. Primary pill buttons: `Hinzufügen` / `Annehmen` (in both the row and the requests section) / `QR zeigen` (now real, was Pattern-A-dampened in Phase 6) / the QR screen's `SegmentedControl` selected-item fill (`fillBrandQuiet`, unchanged component behavior).
5. **New:** the requests-count badge (design `tone="brand"`, L1443) — a SOLID `colors.primary` fill + `colors.textOnPrimary` text, deliberately distinct from the neutral `fillQuiet`/`textMuted` "Bald" badge everywhere else in the app so a real, actionable count reads differently from a decorative placeholder badge.
6. The Sunset gradient ring — reused, **applied to exactly one avatar surface this phase**: the friend detail card's 88px avatar. Not applied to any `PersonRow` avatar (search hit / request / crew, all 40px) — see § Avatar Size Contract "Why the ring stops at the detail card" for the reasoning. This mirrors Phase 6's own restraint: D-07 widens the RULE app-wide, but each phase decides how many identity surfaces it actually has.

Everything else — icons, section headings, plain-text action links, static relation chips, empty-state copy, the search field, the QR mark's dark modules (see § QR & Camera Contract for its two literal, mode-invariant exceptions) — resolves through neutral roles (`textPrimary`/`textSecondary`/`textMuted`/`fillQuiet`/`borderSubtle`).

No new tokens are required this phase. `fillInfoQuiet`/`borderInfo`/`infoText` (added in Phase 6) and `textOnGradient`/`primaryForeground` (already in `tokens.ts`) cover every new surface.

## Search & Add-Flow Contract (D-01–D-04)

- **One field, two requirements.** The existing Friends-screen search field becomes real (`editable={true}`), backed by `GET /visitors?q=` (Phase 7). It satisfies FRND-02 (handle) and FRND-03 (username search) at once — the exact handle is, by construction, the first hit of the prefix search (D-02). There is no separate "enter handle" affordance anywhere on this screen.
- **Debounce & floor (Claude's Discretion, resolved as the DEFAULT):** 300ms debounce; below 2 typed characters the screen shows the "type ≥2 chars" hint (§ Copywriting Contract) and fires no request — a client-side courtesy, not a contract requirement (the 2-char floor is a Phase 7 *service* invariant, not something the contract enforces at 400).
- **Mode switch (D-03).** The instant the field holds ≥1 character, the quiks-code card, Requests block and Crew block are replaced — not just visually hidden, actually unmounted from the scroll flow — by the results list (or its own empty/loading/error state, all below). Clearing the field back to zero characters restores all three blocks exactly as they were.
- **Full relation mapping in the row (D-04).** Every hit renders through the shared `PersonRow` (§ Crew & Friend Detail Contract) with the trailing action mapped 1:1 from `relation`: `none` → Hinzufügen · `requestIncoming` → Annehmen · `requestOutgoing` → Angefragt (static) · `friends` → Freunde (static) · `self` → no trailing element at all. No tap ever routes to a mutation that is guaranteed to fail.
- **Loading/error states** follow the same project-wide "Loading…" text + verbatim transport-error-and-Retry pattern as every other query on this screen — rendered in the same slot the results list would occupy.

## Requests Section Contract (D-07–D-08)

- **One section, two labeled sub-groups**, always both visible: "An dich" (incoming) above "Von dir" (outgoing) — never a `SegmentedControl` between them, so a withdrawn/received request is never hidden behind a toggle the visitor forgot to flip.
- **Badge (D-08).** The section heading "Anfragen" carries a count badge (`colors.primary` fill, `colors.textOnPrimary` text, `r-pill`) showing the **incoming** count only, hidden entirely at 0 — not a `0` badge, no badge element at all.
- **Fixed position (D-08).** Requests is always the third block, after the quiks-code card and before Crew. It never reorders itself to the top when a new request arrives — predictability over urgency, per the explicit user decision.
- **Row actions.** Incoming rows: `Annehmen` (primary pill, same mutation/invalidation as the search-hit "Annehmen") + `Ablehnen` (plain text, `dangerText`, no confirm dialog). Outgoing rows: static `Angefragt` chip + `Zurückziehen` (plain text, `textSecondary`, no confirm dialog) — Phase 7's no-history/no-cooldown model (D-11/D-12) means neither action is destructive enough to warrant `Alert.alert`; only unfriend gets that treatment.
- **Independent empty copy per sub-group** (§ Copywriting Contract) — a visitor with zero incoming but two outgoing requests sees the "An dich" precondition text sitting directly above two real "Von dir" rows, never a shared blank block.

## Crew & Friend Detail Contract (D-09–D-12)

**One radius, not two.** The design gives search/request-style cards `22px` (`r-card`) and the legacy `FriendRow` component `16px` (`r-md`). D-11 mandates ONE shared row block across all three lists, so this spec resolves the conflict toward `r-card` (22px) uniformly — the larger, already-established card radius, matching CI §5's "Kartenradius 22px" guidance for any surface with 14–16px internal padding.

- **Row layout (D-11), identical across search hit / request row / crew row:** `AvatarTile` (40px, § Avatar Size Contract) · `displayName` (`bodyStrong`) · `@username` (`bodySm`, `colors.primary`) stacked, `numberOfLines={1}` + tail-ellipsize on both lines (same long-text guard Phase 6 already applies app-wide) · a trailing action slot (button, static chip, or nothing per context). No presence dot anywhere — ADR-014 excludes it outright, and the design's `f.presence` prop on `FriendRow` is not ported.
- **Sort order (D-12).** Client-side, by `displayName`, ascending. **Concrete implementation risk, not a style note:** `Intl.Collator`/`localeCompare` is not guaranteed correct on Hermes (only `Intl.PluralRules` is polyfilled today, `lib/intl-polyfill.ts`). The sort function belongs in `lib/` as pure, tested logic with an explicit, defined fallback comparator for when `Intl.Collator` is unavailable or behaves as a code-point sort — this is a planner/executor task, flagged here so the UI contract does not silently assume a working locale-aware sort.
- **Tap target (D-09).** Only crew rows are tappable (search hits and request rows are not — `onPress` absent on `PersonRow` for those two lists). A crew-row tap opens `app/friend-detail.tsx` as a modal.
- **Friend detail card contents — exactly what the list already has, nothing more** (Phase 7 D-04: no detail endpoint exists and none is requested): 88px `AvatarTile` wrapped in `AvatarSunsetRing` (the one avatar surface this phase applies the ring to) · `displayName` (`title2`) · `@username` (`countdown`, `colors.primary`) · identity line via `buildIdentityLine({ pronoun, gender })` (age always `undefined` — the foreign view carries no `birthDate`) · "Freunde seit {date}" from `friendsSince` (locale-formatted via `Intl.DateTimeFormat`, not a raw ISO string) · at the bottom, the `Freundschaft beenden` danger row (§ Copywriting Contract).
- **Why the ring stops at the detail card.** Applying the Sunset gradient ring to all three `PersonRow` avatars (potentially dozens on one scroll) would read as gradient noise inside a scrolling list and works against CI §3's "maximal zwei Flächentöne pro Screen" spirit even though D-07's rule technically permits it. The detail card is this phase's one true "identity surface" (the same role the Profil header plays) — matching Phase 6's own precedent of applying the ring to exactly the surfaces that need it, not everywhere the rule allows it.
- **After unfriend**, the modal closes (`router.back()`) and the crew list reflects the removal without a manual refresh (success criterion 2/3) — the exact invalidation strategy (optimistic vs. refetch-on-close) is Claude's Discretion, left to the planner.

## QR & Camera Contract (D-13–D-17)

- **One screen, one switcher.** `app/friends-qr.tsx` renders a `SegmentedControl` (`Mein Code` / `Scannen`, reused component, unchanged props) at the top, screen padding `layout.screenPad`. Below it, exactly one of two panels renders — never both, never a third state.
- **"Mein Code" panel:** the visitor's own `@username` (from the existing shared `['me']` query, extended not duplicated) rendered as a real, scannable QR mark encoding `quiks:u/<username>` (namespaced plaintext, Phase 7 D-17 — **not** a deep link), plus the body copy from § Copywriting Contract. Opens by default (D-13).
  - **Scannability is a hard requirement, not a style choice.** The QR mark renders on a FIXED white backdrop with FIXED dark modules in BOTH color modes — `colors.primaryForeground` (`#FFFFFF`, mode-invariant) for the backdrop card, `colors.textOnGradient` (`#0C0E13`, mode-invariant) for the modules. Both tokens already exist in `tokens.ts`; **no new token is needed.** This is a deliberate, documented exception to "no raw hex in component code" for exactly this one surface — a theme-tinted or inverted QR mark is a real-world scan-failure risk a visual-consistency rule should not override.
  - Backdrop card: `r-md` (16px) radius, generous internal padding (`sp-8`, 24px) around the mark so the quiet zone a scanner needs is never violated by the card edge.
  - Missing handle (brand-new account, no username yet) → the edge-case copy above renders instead of an empty/broken mark; no fallback graphic is invented.
- **"Scannen" panel:** the camera preview mounts ONLY while this panel is active — switching back to "Mein Code" or leaving the screen tears the camera down. Three sub-states:
  1. **Permission not yet requested / requesting** — switching to this tab triggers the OS permission prompt immediately (D-15, no separate rationale screen); while the promise is pending, render the same project-wide "Loading…" text pattern.
  2. **Granted** — a full-bleed camera preview with a centered scan-target overlay (a simple square outline, `borderColor: colors.primaryForeground` at reduced opacity over the live feed — decorative only, not a themed surface since it sits on unpredictable live video).
  3. **Denied** — a full replacement of the camera area (D-16), styled as an info callout (`fillInfoQuiet` background, `borderInfo` border, `infoText` icon `CameraOff` + heading, `r-card` radius): rationale text, `Einstellungen öffnen` primary pill, `Stattdessen Handle eingeben` plain-text link that routes back to the Friends screen with the search field focused. This state is reachable and permanent on Android after a hard denial — it must never be a dead end.
- **On successful decode (D-14):** the payload is validated as `quiks:u/<handle>` before any network call (pure logic, belongs in `lib/`, testable off-device per the established pattern). A valid handle triggers `GET /visitors/:username` and renders the confirmation card (§ Copywriting Contract) using the SAME `PersonRow`-style info block plus the same D-04 relation-mapped action set — never an immediate, unreviewed request send. An invalid payload or a 404 lookup shows its own inline error + "Nochmal scannen" without leaving the panel.
- **Library selection is explicitly out of scope for this document** (Claude's Discretion in `08-CONTEXT.md`): `expo-camera` is not yet in `apps/mobile/package.json` and a QR-generation approach on top of the already-present `react-native-svg` (`~15.15.5`) is unbuilt. Both require `npx expo run:android` from `apps/mobile` before device testing (the mmkv/NitroModules precedent from Phase 5). This spec fixes what the two panels must look like and contain — not which package renders them.

## Avatar Size Contract

`AvatarTile`'s `AVATAR_SIZE` constant (88px) stays the default and unchanged for the Profil header and the friend-detail card. This phase adds a `size` prop:

- `size={40}` — used by every `PersonRow` instance (search hit / request row / crew row), matching the design's `size="40"` `Avatar` usage (L1447/1459/1473/1483).
- Initials text at `size={40}` resolves through the `label` role (13.5/700, body font) instead of `title2` (26/700) — `title2` text does not fit inside a 40px circle. Border width (2px) and `fillBrandQuiet`/`primary` colors are unchanged at both sizes — only geometry and the initials font role scale.
- `deriveInitials()` is unchanged and reused as-is at both sizes.
