# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note (read first)

Unlike Phase 3 (explicitly unstyled placeholder screens, D-01/D-04), this phase has **real,
pixel-precise Claude Design mockups** as its source of truth: `docs/concept/designs/auth/`
(8 frames, dark+light, imported 2026-08-04, referenced from `docs/concept/09-onboarding-auth.md`).
Open `docs/concept/designs/auth/preview.html` to see them rendered. This UI-SPEC transcribes
those mockups into an implementable RN contract and resolves every gap between "what the mockup
shows" and "what actually needs to be built" so the executor does not have to guess.

**This phase supersedes `packages/ui/src/tokens.ts`'s placeholder values.** That file's own header
comment says: "Replace them with the real festipal design system once the designs from Claude
Design are available." They now are. The Spacing/Typography/Color sections below are the REAL
brand tokens (`docs/concept/designs/auth/source/festipal-tokens.css`, `docs/concept/03-design-
system.md`, binding per ADR-015) — the plan must update `packages/ui/src/tokens.ts` to match
these values (not invent a third, competing set), since Phases 5/6 will keep building on it.

**Resolved decisions (no user confirmation needed — traced to existing binding docs):**

1. **Source-string language stays English (D-08, unchanged).** The DE catalog is the
   translation, but for these specific screens the DE text must match the mockup **verbatim**
   (mockup = "binding German concept term" per D-08's own rule, since it was authored in
   Claude Design in German). EN source strings are authored fresh where Phase 3 had none, and
   reused unchanged where Phase 3 already shipped an equivalent string (see Copywriting Contract
   — rows marked "unchanged from Phase 3" vs "new this phase" vs "DE-only revision").
2. **v1/v2 scope trim:** the mockup's Profil-screens (04a/b/c) include a **social-links block**
   (Instagram/Spotify) and a **profile-visibility segmented control** (Nur ich/Freunde/Alle).
   `REQUIREMENTS.md` v1 `IDN-01` scopes first-login completion to **username + displayName +
   optional avatar only**; `socials[]`/`socialsVisibility` is explicitly `PROF-02` (v2, deferred).
   **Both blocks are excluded from the Phase 4 screen** — REQUIREMENTS.md's 2026-07-30
   reconciliation is the later, authoritative scope decision over the concept doc's earlier
   full-featured mockup. Do not build them now.
3. **Routing restructure required:** today `(auth)/index.tsx` IS the email-entry form (Phase 3
   never built a separate Welcome screen). This phase's mockup frame 01 is a NEW first screen.
   `(auth)/index.tsx` becomes **Welcome**; the existing email-entry logic moves to a new route
   (e.g. `(auth)/email.tsx`); `(auth)/verify.tsx` stays the OTP route, reached from Welcome →
   Email → Verify.
4. **OTP interaction pattern changes from Phase 3.** Phase 3 deliberately chose one real
   `TextInput` over six boxes ("overflow-impossible" reasoning, 03-04). The mockup visually shows
   six separate digit boxes with no submit button. **Both are preserved simultaneously**: keep
   ONE real (possibly visually hidden/zero-opacity) `TextInput` capturing the numeric input
   (`maxLength=6`, `keyboardType="number-pad"`, `autoComplete="one-time-code"`), and render **six**
   `View` boxes reading off its current value to display each digit — the standard RN OTP-box
   pattern. This satisfies the mockup's visual fidelity requirement AND keeps Phase 3's
   overflow-impossible/no-real-multi-input reasoning intact.
5. **OTP auto-submits — no "Verify" button.** The mockup's screen 03/03b render no submit button
   at all. Verification fires automatically the instant the 6th digit is entered. Phase 3's
   `Verify`/`Verifying…` strings are dropped from this phase's scope (superseded, see Copywriting
   Contract). A loading state still needs a visual: all 6 boxes go to a muted, non-interactive
   state while the verify call is in flight (no new copy — silently async; only a genuine error
   produces visible copy, matching frame 03b).
6. **Resend gets a countdown, not an always-tappable link.** Mockup shows "Erneut senden in
   0:42" (disabled, timer icon) during a cooldown. Default the cooldown to **60 seconds**
   (Claude's technical default — the mockup only shows a mid-countdown snapshot, not the exact
   starting value; the resend cooldown is a client-side UX nicety, the source of truth for
   legitimate OTP validity/rate-limiting is still the API's built-in rate limiter from Phase 2).
   After the countdown reaches 0, the text becomes a tappable "Code erneut senden" link
   (authored, not pictured — the mockup's own footer explicitly lists "der Rate-Limit-Fall" as
   "noch nicht dabei", i.e. only the send-a-new-code UI is designed, not every downstream state).
7. **Screens use `headerShown: false` + an in-body H1**, not the native Stack header title. The
   mockup shows either a bare circular back-button with no title text (Email, Code) or nothing at
   all (Welcome, Profile). The old `Stack.Screen options={{ title: t\`...\` }}` pattern from Phase
   3 is kept ONLY as the screen's accessibility label (still useful for iOS back-swipe / screen
   reader), not as visible chrome. The mockup's H1 (e.g. "Deine E-Mail") is the real, visible
   title, rendered in-body.
8. **Dark-first, light fully supported, no manual toggle this phase.** `festipal-tokens.css`'s
   own comment says "Festipal is dark-first"; `docs/concept/03-design-system.md` §2 says both
   modes are full team-decided requirements and must follow system setting. Phase 4 wires colors
   via RN's `useColorScheme()` (system-driven), defaulting visually to the dark palette (matches
   the mockup's primary/first-shown mode). A manual light/dark switcher is a Settings-screen
   feature not scoped to any Phase 4 requirement — deferred, non-blocking.
9. **Logout (AUTH-04) has no mockup** (out of scope of the 8 imported onboarding frames — logout
   isn't an onboarding step). Placed as a new icon-only button (top-right) on the existing
   Festivals list screen header (the only authenticated shell surface that exists until Phase 6's
   real Profile screen) — see Copywriting Contract "Logout".
10. **New dependencies this phase** (none currently installed — verified against
    `apps/mobile/package.json`): `lucide-react-native` + `react-native-svg` (icons — back arrow,
    mail, timer, alert-circle, check, x, image, camera, rotate-ccw, log-out), `expo-image-picker`
    + `expo-image` (avatar photo/camera picker), a font-loading mechanism for Outfit / Plus
    Jakarta Sans / JetBrains Mono (e.g. `@expo-google-fonts/*` + `expo-font`, OFL-licensed per
    doc 03 §8) with graceful system-font fallback until loaded (non-blocking on the splash gate).

## Spacing Scale

**Full ported scale** (`--sp-*`, `festipal-tokens.css`) — this phase adopts the REAL,
already-approved 12-step brand scale in full rather than force-fitting it into the generic
4/8/16/24/32/48/64 default, because it is a ported brand system (ADR-015), not invented for this
phase. Do not round these to the nearest multiple of 4.

| Token | Value | Usage this phase |
|-------|-------|-------------------|
| sp-2 | 4px | Icon-to-text inline gaps (status icon next to helper text, "@" prefix to username value) |
| sp-4 | 8px | Compact gaps (avatar-action buttons row, gap between OTP boxes ≈9px) |
| sp-5 | 12px | Field-to-helper-text gap, avatar-tile-to-actions gap |
| sp-6 | 16px | Default field-to-field gap within a form section |
| sp-7 | 20px | Top screen padding (below status bar / header) |
| sp-8 | 24px | Bottom screen padding, inter-section gaps (avatar block ↔ form fields ↔ CTA) |
| sp-9 | 32px | Welcome-screen vertical rhythm (wordmark block ↔ CTA block) |

Named layout constants (not part of the `sp-*` ramp, used as-is):

| Constant | Value | Usage |
|----------|-------|-------|
| `--screen-pad` | 18px | Fixed horizontal gutter on every screen — all fields/buttons/text align to this, NOT `sp-6`/16px. Deliberate 2px-off-scale value from the approved brand system. |
| `--hit-min` | 44px | Minimum tap target — applies to every `Pressable` (back button, avatar photo/camera buttons, resend link, logout icon-button) even when the visual glyph is smaller (e.g. the 36px camera icon button needs 44px hit-slop padding) |
| `--content-max` | 430px | Design reference width (iPhone), NOT a hard RN layout constraint — screens stay `flex:1`/fluid on real devices of any width |

Exceptions:
- `sp-1` (2px) and `sp-3` (6px) exist in the ported scale for hairline/icon micro-nudges only —
  not used as layout spacing on this phase's screens; do not introduce new uses of them.

**Shape:** buttons and segmented-control tracks use `--r-pill` (9999px, fully rounded); input
fields and OTP boxes use `--r-control` (12px); the inline error/info box uses `--r-md` (16px).
Nothing on these screens is square-cornered (doc 03 §4: "Nichts ist eckig").

### Deviation — approved (ADR-015)

This section declares **11 type roles, 9 distinct sizes (56 / 34 / 27 / 21 / 17 / 15 / 13.5 /
12 / 10.5px) and 5 weights (800 / 700 / 600 / 500 / 400)** — deliberately exceeding the generic
UI-SPEC max-4-sizes / max-2-weights heuristic. This is an **explicit, documented exception, not
an oversight**, and it is APPROVED on the following grounds:

- **Ported verbatim, not authored this phase.** The full role set is transcribed 1:1 from the
  approved Claude Design brand system — `docs/concept/03-design-system.md` §3 (binding as
  **ADR-015**) and the token file `docs/concept/designs/auth/source/festipal-tokens.css`, as
  rendered in the imported mockups `docs/concept/designs/auth/`. None of these sizes/weights were
  invented for Phase 4; they are the project's real, pre-existing, already-signed-off typographic
  system.
- **Non-reducible without breaking visual fidelity.** Collapsing the scale (e.g. merging the 56px
  wordmark, 34px H1, 21px tagline, and 17px button into "3-4 sizes", or dropping the 800/500
  weights) would make the implemented screens diverge from the approved mockups. **Design
  Fidelity is a non-negotiable architecture principle** (CLAUDE.md Principle 5: "the frontend
  follows the designs the user creates in Claude Design; match them precisely"), which overrides
  the generic heuristic here.
- **Planner/executor directive:** treat the full 11-role set above as **LOCKED**. Do NOT collapse
  it toward the 4-size / 2-weight default, and do NOT introduce any size or weight not in the
  table. The heuristic is satisfied by this written justification, not by reducing the scale.

## Color

Dark is the default rendering mode (system-driven via `useColorScheme()`); light is fully
supported with the same semantic token names resolving to different values. No manual toggle
ships this phase (see Scope note #8).

| Role | Token | Dark | Light | Usage |
|------|-------|------|-------|-------|
| Dominant (60%) | `--bg-app` | `#0C0E13` | `#FFFFFF` | Screen background |
| Secondary (30%) | `--surface-inset` | `#07080B` | `#E9ECF2` | Input fields, OTP digit boxes |
| Secondary (30%), alt | `--surface-card` | `#14161D` | `#FFFFFF` | Card-like containers (reserved; no card surface on this phase's screens beyond inputs) |
| Accent (10%) | `--ci-primary` (= brand green-500) | `#74CC1F` | `#74CC1F` | Primary CTA fill + glow, focused-field border + focus ring, OTP active-digit border + blinking caret, avatar-tile ring/tint |
| Success | `--status-success` (green-400) | `#8FDA3B` | `#8FDA3B` | Username-available check icon + helper text ONLY |
| Destructive | `--status-danger` (red-500) | `#FF4D5E` | `#FF4D5E` | Error states only: wrong/expired-OTP box border + inline error box, username-taken field border + icon + helper text |
| Text primary | `--text-primary` | `#E9ECF2` | `#07080B` | Headings, field values |
| Text secondary | `--text-secondary` | `#9FA6B6` | `#363B49` | Subtitles, field labels |
| Text muted | `--text-muted` | `#7C8394` | `#565C6E` | Placeholder-weight helper text, disabled icon tint |

Accent (`--ci-primary`) reserved for **exactly these elements, nothing else**:
- Primary CTA fill + glow-shadow ("Los geht's" / "Code senden" / "Neuen Code senden" / "Fertig")
- Focused `TextInput` border + focus ring (email field, username field)
- OTP active-digit box border + blinking text caret
- Avatar-tile background tint + ring (the initials-fallback circle)

Success (`--status-success`) reserved for the username-available check icon + its one line of
helper text ONLY — not reused as a generic "OK" color elsewhere.

Destructive (`--status-danger`) reserved for **exactly**: OTP digit boxes + inline error box on
wrong/expired code; username-field border + icon + helper text on the "taken" state. **Not** used
for logout — logout is a neutral, reversible, non-destructive action (no confirmation dialog, see
Copywriting Contract "Logout").

Status colors are always applied as a 16% tint behind colored text/border, never as a solid fill
(doc 03 §2) — this is already how the mockup renders the error box (`rgba(255,77,94,.12)` fill +
solid border) and the username-taken field (`rgba(255,77,94,.08)` fill).
