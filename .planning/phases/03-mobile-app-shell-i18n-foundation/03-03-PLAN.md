<objective>
Wire the two shared clients (`lib/auth-client.ts`, `lib/api-client.ts`) and expand the root layout
into the splash-held, four-state auth guard that gates the three route groups.

Purpose: This is the auth-to-API spine. RESEARCH names one integration point as close to
load-bearing as anything in the phase: getting the session cookie from better-auth's Expo client
(SecureStore-backed, no native RN cookie jar) into the ts-rest client's requests. Get it wrong and
login appears to work while every subsequent API call silently 401s (Pitfall F). The guard must
also branch on THREE authenticated-or-not states, not two, and hold the splash until both session
and profile resolve (Pitfall 5) so no wrong route flashes on cold start (SC-2).

Output: the auth client, the cookie-forwarding API client, and the three-way route guard skeleton.
</objective>

### Route-group / guard decision (CONTEXT Claude's-Discretion; RESEARCH Open Question 1)
The guard branches into four states. The `authenticated-no-profile` branch routes to a
`(profile-setup)` group (a minimal real stub built in Plan 04, recommendation (a) from RESEARCH) so a
genuinely first-time OTP account — whose `GET /me` returns `profile: null` — is not a dead-end and
D-02/D-03 are demonstrable end-to-end. Route-group guard mapping:
- unauthenticated → `(auth)`
- authenticated-no-profile → `(profile-setup)`
- authenticated → `festivals` + `(festival)`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Expo client → `/api/v1/*` | Every authenticated request must carry the SecureStore session cookie; the API's own AuthGuard is the real boundary (Phase 2). |
| SecureStore session jar | Encrypted OS-keychain storage of the session token; the only acceptable store. |
| Client-side route guard | UX/defense-in-depth against deep-link access — not a substitute for server-side scoping. |

## STRIDE Threat Register (ASVS L1, block on high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-06 | Information Disclosure | Session storage | high | mitigate | `expo-secure-store` only via `expoClient({ storage })`; no AsyncStorage/MMKV (Pitfall 2). |
| T-03-07 | Elevation of Privilege | Deep-link into protected route | medium | mitigate | Group-layout `Stack.Protected` guards re-evaluate on every navigation incl. deep links (Pitfall 5); server AuthGuard remains the real boundary. |
| T-03-08 | Spoofing | Cookie forwarding | high | mitigate | Cookie sourced only from `authClient.getCookie()` (server-issued); `credentials: 'omit'` prevents the RN fetch from garbling it (Pitfall F). |
</threat_model>
