# Phase 05.1 Plan 03: CI-v1.0-Fundament Summary

**Der Gerätemodus löst jetzt über eine getestete reine Funktion in einen Context auf — hell ist der Standard, `'dark'` der einzige Auslöser für Dunkel — und die Werte, die dieser Pfad auflöst, sind quiks CI v1.0 in beiden Modi, mit einer Typoskala, in der jede Rolle auf eine echte Gewichtsdatei zeigt.**

## Accomplishments

- **Der Moduspfad existiert überhaupt erst.** Vor diesem Plan gab es in `apps/mobile` keinen einzigen `useColorScheme`-Aufruf und `lightColors` war ein toter Export (Brand-Doku §9a). Jetzt: `useColorScheme()` → `resolveThemeMode` → `ThemeProvider` → `useTheme()`. Nur der exakte Wert `'dark'` ergibt Dunkel; `'light'`, `null`, `undefined` und RNs `'unspecified'` ergeben Hell — festgenagelt durch fünf Einzeltests plus eine Aussage darüber, dass **genau ein** Eingabewert Dunkel liefert.
- **Der Context kann keine undefinierten Farben liefern.** Sein Default ist `resolveTheme(null)`, also ein echtes helles Theme. `useTheme()` außerhalb eines Providers wirft nicht und gibt nichts Leeres zurück — das ist die UI-SPEC-E3/loading-Garantie, dass das FloatingNav-Glas nie transparent über Seiteninhalt malt. Getestet über `bgApp`/`glassFill`/`glassBorder`.
- **`userInterfaceStyle` von `light` auf `automatic`.** Ohne diese eine Zeile hätte das OS das gemeldete Schema fixiert: sämtliche Unit-Tests wären grün geblieben, während der Moduswechsel auf dem Gerät tot gewesen wäre.
- **Der Splash folgt dem Modus (D-02).** `SplashView` baut seine Styles über `useMemo(() => createSplashStyles(colors), [colors])` statt aus einem modulweiten `StyleSheet.create`, das seine Farben beim Import einfriert. Hintergrund `bgApp`, Wortmarke `textPrimary`, Punkt in **beiden** Modi Beere (CI §7: den Punkt nie wie das Wort einfärben). Dafür wurde das Root-Layout in eine dünne Provider-Hülle geteilt — der Splash-Zweig liegt vor dem `bootstrapped`-Gate und wäre unter einem tiefer platzierten Provider ungethemed geblieben.
- **CI v1.0 in `tokens.ts`, mit Herkunftsnachweis.** Beere/Amber als Primär/Sekundär, Weiß auf Beere, Ink auf Amber, Papier/Ink als Flächen, Karte weiß bzw. 6 % Weiß, eigenes helles Glas-Paar statt Vererbung. Jeder Wert, der nicht wörtlich im Brand-Dokument steht, trägt einen inline `derived`-Marker — die Konvention aus §8 des Brand-Dokuments fortgesetzt, damit ein späteres Review bindende Vorgabe und Interpolation unterscheiden kann.
- **Limette und Violett sind weg, und das ist eine Testaussage.** Der D-11-Gate-Test iteriert **beide** Farbsets rekursiv (auch verschachtelt in `gradientSunset`) und schlägt fehl, sobald einer der beiden Hex-Werte zurückkehrt. Kein `ciFallbacks`-Export.
- **Sunset als Daten, nicht als Stylesheet-Schnipsel.** `gradientSunset` trägt Winkel, objectBoundingBox-Vektor und zwei geordnete Stops, damit der `react-native-svg`-Konsument (Plan 04) und der Node-Icon-Generator (Plan 06) dieselben Zahlen lesen. `textOnGradient` = Ink beantwortet RESEARCH-Open-Question 1 im Code: Weiß versagt an **jedem** Punkt des Verlaufs.
- **Vier Status-Textvarianten, weil Hell-first sie erzwingt.** `danger` erreicht als Text auf Papier nur 2,98:1. `dangerText`/`infoText`/`successText`/`warningText` sind modusabhängig (im Dunkelmodus identisch mit ihrer Füllfarbe) — die Regel „bare Hue = gefüllte Fläche, `*Text` = Text/Icon/1px-Rand" steht als Kommentar direkt über den Tokens, weil die Plans 04/05 sie anwenden müssen.
- **Kein synthetisches Fett mehr.** `fontFamilyForRole` bildet jede der zwölf Rollen auf eine echte Gewichtsdatei ab; drei neue Gewichte (`Outfit_800ExtraBold`, `PlusJakartaSans_700Bold`, `JetBrainsMono_500Medium`) sind registriert, **ohne** eine Installation — alle drei lagen bereits in den installierten `@expo-google-fonts`-Paketen. Das Mapping ist ein totales `Record<TypeRole, string>`: eine neue Typo-Rolle ohne Schriftentscheidung ist ein Compile-Fehler, kein stiller Fallback auf die Systemschrift.

## Decisions Made

- **`ThemeColors` als gewidmeter Mapped Type.** Der Plan schrieb `export type ThemeColors = typeof tokens.colors` vor. Das ist nicht typprüfbar: beide Token-Objekte sind `as const`, also ist `colors.bgApp` der Literaltyp `'#0C0E13'` und `lightColors.bgApp` `'#F7F5F2'` — das helle Set wäre dem Typ des dunklen nie zuweisbar gewesen. Gelöst über `{ readonly [K in keyof typeof colors]: (typeof colors)[K] extends string ? string : (typeof colors)[K] }`: der **Schlüsselsatz** bleibt tragend (eine fehlende Rolle ist weiterhin ein Typfehler), Stringwerte werden auf `string` geweitet, und `gradientSunset` behält seine präzise Form, damit Konsumenten die Stops sehen.
- **`'unspecified'` gehört zum Auflösungsvertrag.** RN 0.86s `ColorSchemeName` enthält `'unspecified'`; die im Plan vorgesehene Signatur `'light' | 'dark' | null | undefined` schlug im Typecheck fehl. Statt eines Casts wurde der Eingabetyp geweitet — `'unspecified'` ist inhaltlich derselbe „keine Präferenz gemeldet"-Fall wie `null` und ergibt hell. Ein zusätzlicher Test deckt ihn ab.
- **`DeviceColorScheme` lokal deklariert statt RNs `ColorSchemeName` importiert.** Ein Typimport aus `react-native` hätte den node-importierbaren Charakter von `lib/theme.ts` gefährdet (und den Grund, warum der Resolver überhaupt dort liegt). Der Union ist klein und im Kommentar an seine Quelle gebunden.
- **`gradientSunset` liegt innerhalb von `colors`.** Damit ist er per Spread automatisch modus-invariant, über `useTheme().colors.gradientSunset` erreichbar und Teil des D-11-Scans. Der Scan musste dafür rekursiv werden — ein flacher `Object.values`-Vergleich hätte einen verschachtelten Hex-Wert übersehen, also genau das Schlupfloch offen gelassen, das das Gate schließen soll.
- **Dunkles `muted` von `#14161D` auf `rgba(255,255,255,.06)`.** Der Plan verlangt, dass „kein Wert der Alt-Palette irgendwo in der Datei überlebt". `#14161D` war der alte dunkle `surfaceCard`-Wert; nachdem dieser laut CI §6 zu „6 % Weiß" wird, wäre `muted` der letzte Rest gewesen. Als `derived` markiert.
- **`success` bleibt `#8FDA3B`, `warning` bleibt Amber** — beide Entscheidungen stammen aus dem Plan-Objective und sind jetzt **inline im Token** begründet, damit die Limette-Rampen-Herkunft des Grüns später nicht als Versehen gelesen wird. Zur Geräte-Sichtprüfung in Plan 05.1-07 angemeldet.
- **`otpDigit`/`countdown` bewusst nicht angefasst.** Beide deklarieren Gewicht 500, laden aber die 400er-Datei. Der UI-SPEC erklärt das ausdrücklich als phasenfremd; ein stiller Wechsel auf `JetBrainsMono_500Medium` hätte die OTP-Boxen verändert, ohne dass ein Plan dieser Phase das abgenommen hat. Als „KNOWN FOLLOW-UP" im Code dokumentiert und im Test als solcher kommentiert.
