# quiks — Post-Merge-Rename-Checkliste (D-15)

> **Diese Checkliste wird NICHT während der Phase ausgeführt.** Sie ist eine
> Entwickler-Handlung **nach dem Merge** dieser Phase. Kein Schritt darin wurde von der
> Phasenausführung angefasst — `git remote -v` zeigt am Phasenende unverändert die alte URL.

**Warum am Ende und nicht mittendrin (D-15):** Ein Rename des Arbeitsverzeichnisses bricht
laufende Pfade, offene Terminals und den Metro-/Expo-Watcher. Alles, was während der Phase
gegen absolute Pfade lief (Metro, Gradle-Daemon, IDE-Indizes, offene Shells), zeigt danach ins
Leere. Deshalb: erst die Phase abschließen und mergen, dann umbenennen.

**Umfang:** Diese Checkliste schließt den letzten offenen Punkt von ADR-024 — Repo-Verzeichnis
und Git-Remote. Der gesamte Code-, Infra- und Identifier-Rename (npm-Scope, Expo
`name`/`slug`/`scheme`, Bundle-ID, MMKV-IDs, `docker-compose.yml`) ist bereits in den Plänen
05.1-01 und 05.1-02 erledigt und gemerged.

### 2. Repository auf GitHub umbenennen

- [ ] `emilauer99/festipal` → `emilauer99/quiks`
      (GitHub → Repository → *Settings* → *General* → *Repository name* → *Rename*).
- [ ] GitHub legt automatisch eine Weiterleitung von der alten URL an. Sie ist ein
      Sicherheitsnetz, **kein Ersatz** für Schritt 3: die Weiterleitung verschwindet, sobald
      jemand ein neues Repo unter dem alten Namen anlegt.

### 3. Lokale Remote-URL setzen und mit einem Fetch verifizieren

```bash
git remote set-url origin https://github.com/emilauer99/quiks.git
git remote -v            # beide Zeilen müssen .../quiks.git zeigen
git fetch origin         # muss ohne Fehler durchlaufen
```

- [ ] `git remote -v` zeigt zweimal die neue URL.
- [ ] `git fetch origin` läuft fehlerfrei durch.

> Der Fetch ist der eigentliche Test. `set-url` schreibt nur in `.git/config` und schlägt auch
> dann nicht fehl, wenn die URL gar nicht existiert.

### 4. Alle Prozesse im alten Verzeichnis beenden, dann den Ordner umbenennen

- [ ] Metro/Expo beenden (`npx expo start`, `expo run:android`) — **zuerst**. Ein laufender
      Watcher ist auf dieser Maschine die dokumentierte Ursache für `ENOENT`-Fehler auf
      pnpms Temp-Verzeichnissen (Projektgedächtnis, Phase 3).
- [ ] Gradle-/Java-Daemons beenden, falls ein Android-Build lief.
- [ ] Alle Terminals schließen, deren Arbeitsverzeichnis unterhalb des alten Ordners liegt.
- [ ] IDE (JetBrains/VS Code) schließen — sie hält Indizes und Dateihandles auf den alten Pfad.
- [ ] Docker-Stack darf laufen bleiben: er hängt seit Plan 05.1-02 **nicht mehr** am
      Ordnernamen (siehe Schritt 5).
- [ ] Ordner umbenennen:
      `C:\Users\Emil\Documents\Privat\Projekte\festipal` → `...\Projekte\quiks`.

> Unter Windows scheitert ein Rename mit *„Zugriff verweigert"*, solange **irgendein** Prozess
> ein Handle auf ein Verzeichnis darin hält. Wenn es hakt, ist noch etwas offen — kein Grund,
> mit Gewalt zu arbeiten, sondern der Hinweis, dass ein Punkt oben übersprungen wurde.

### 5. Neu öffnen und verifizieren

```bash
cd C:\Users\Emil\Documents\Privat\Projekte\quiks
pnpm install
docker compose ps
docker volume ls | grep quiks
pnpm --filter ./apps/api test
```

- [ ] `pnpm install` läuft sauber durch.
- [ ] **`docker compose ps` zeigt weiterhin `quiks-postgres-1` und `quiks-mailpit-1` als
      `healthy`** — und `docker volume ls` weiterhin **`quiks_quiks-postgres-data`**, also
      dasselbe benannte Volume wie vor dem Rename.
- [ ] `pnpm --filter ./apps/api test` ist grün (45 Tests). Das ist der eigentliche Beweis: die
      Suite läuft gegen die echte lokale Datenbank. Wäre Compose auf ein neues, leeres Volume
      gewechselt, fiele sie hier durch, statt still zu bleiben.

> **Warum das überhaupt gutgeht (T-05.1-16):** `docker-compose.yml` trägt seit Plan 05.1-02
> einen expliziten `name: quiks`-Schlüssel. Ohne ihn leitete Compose den Projektnamen aus dem
> **Ordnernamen** ab — nach diesem Rename also plötzlich aus `quiks` statt `festipal`, was das
> in Plan 05.1-02 zurückgesetzte, migrierte und geseedete Volume kommentarlos verwaist und
> beim nächsten `up` ein leeres neues angelegt hätte. Genau dagegen ist der `name:`-Schlüssel
> gesetzt; die zwei Prüfungen oben belegen, dass er greift.
