## Fixed Issues

### CR-01: Four newly-added strings ship untranslated (English) in the German catalog

**Files modified:** `apps/mobile/locales/de/messages.po`, `apps/mobile/package.json`
**Commit:** `6023cff`
**Applied fix:** Filled the four empty German `msgstr` entries sourced from
`FloatingNav.tsx`: `Home` → `Start`, `Friends` → `Freunde`, `Profile` → `Profil`,
`coming soon` → `bald verfügbar`. Added `--strict` to the `compile` script in
`apps/mobile/package.json` (`lingui compile` → `lingui compile --strict`) so an
incomplete catalog fails the build instead of silently falling back to English, per
the review's fix suggestion. Verified with `npx lingui compile --strict`, which now
passes with 0 missing translations (previously failed with "Missing 4
translation(s)").

### WR-01: Concurrent Save mutations can roll back a different festival's in-flight optimistic cache entry

**Files modified:** `apps/mobile/app/(tabs)/festivals.tsx`
**Commit:** `2735700`
**Applied fix:** Rewrote `saveMutation`'s `onError` to reconcile against the
*current* `festivalKeys.mine` cache instead of restoring the exact snapshot
captured at `onMutate` time. The new handler filters the current cache by
`festival.id`, removing only the optimistic entry this specific mutation call
added. To avoid a related edge case not explicitly called out in the review (a
festival that was already saved before this call — dedup guarded via
`alreadySaved` in `onMutate`), the fix additionally checks the mutation's own
`context.previous` to determine whether this call actually added the entry
(`wasAlreadySaved`), and skips the removal if it was already present. This keeps a
concurrent, still-in-flight or already-succeeded save for a different festival
safe from a sibling mutation's failure, without reintroducing the "leave a stale
already-saved entry visible after its own genuine removal fails" case the review
didn't flag but which the naive "always filter" version from the review's example
snippet could have introduced.

### WR-02: Inconsistent guarding around synchronous MMKV storage calls

**Files modified:** `apps/mobile/lib/active-festival-storage.ts`
**Commit:** `69e7a9f`
**Applied fix:** Took the review's suggested "shared helper" option rather than
wrapping all four call sites individually: moved the `try { … } catch { … }` guard
into `saveActiveFestivalSlug`, `getActiveFestivalSlug`, and
`clearActiveFestivalSlug` themselves (in `active-festival-storage.ts`), so every
current caller (`festivals.tsx`'s `handleEnter`/`handleLogout`,
`[festivalSlug].tsx`'s focus effect, `_layout.tsx`'s cold-start redirect, and
`home.tsx`'s already-guarded call) and any future caller gets the "gate-less entry
must never dead-end on a synchronous MMKV throw" guarantee for free, instead of
relying on each call site remembering to wrap it. `home.tsx`'s existing local
`try/catch` was left untouched (redundant but harmless, and out of this finding's
file scope) to keep the diff minimal.
